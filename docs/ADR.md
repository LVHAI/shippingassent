# 运费助手 — 架构决策记录 (ADR)

## ADR-001: 采用混合架构（确定性计算 + RAG）

**状态**: 已采纳
**日期**: 2026-09-02

### 背景

运费数据来源 Excel，包含两类信息：
1. **结构化费率表**：重量区间、单价、处理费，数据天然确定性
2. **非结构化规则文本**：尺寸限制、赔偿标准、禁运品说明等

### 决策

- 费率数据 → SQLite 结构化存储 → SQL 精确查询 → 确定性计算
- 规则文本 → Embedding → Milvus 向量检索 → LLM 生成解释

**不采用**纯 RAG 方案（所有内容向量化后由 LLM 生成答案），因为：
- LLM 可能产生幻觉，编造不存在的价格
- 向量检索对数值精度不敏感，无法精确匹配重量区间
- 运费报价错误直接影响客户信任和商业利益

### 后果

- ✅ 运费计算 100% 精确，无幻觉风险
- ✅ 规则解释仍有 LLM 润色，用户体验好
- ⚠️ 需要维护两套存储系统（SQLite + Milvus）
- ⚠️ XLS 解析需要同时提取结构化数据和文本数据

## ADR-002: 使用 LangGraph 条件路由而非线性链

**状态**: 已采纳
**日期**: 2026-09-02

### 背景

用户查询有多种模式：精确报价、规则查询、混合查询、信息不完整需追问、闲聊。

### 决策

使用 LangGraph 构建有向图工作流，包含条件路由节点：

```
意图识别 → 路由分支：
  ├── 参数不完整 → 追问
  ├── 费率查询 → 费率计算 → 生成
  ├── 规则查询 → 向量检索 → 生成
  ├── 混合查询 → (费率计算 ∥ 向量检索) → 生成
  └── 闲聊 → 直接生成
```

**不采用**简单的线性链（intent → retrieve → generate），因为：
- 不同查询类型需要不同的处理路径
- 参数不完整时需要中断并追问，不是所有查询都能直接执行
- 混合查询需要并行执行多个工具

### 后果

- ✅ 每种查询类型走最优路径
- ✅ 支持多轮对话和追问
- ⚠️ 工作流复杂度高于线性链
- ⚠️ 需要定义清晰的 State 和路由条件

## ADR-003: Milvus Lite 而非 Milvus Standalone

**状态**: 已采纳
**日期**: 2026-09-02

### 背景

需要向量数据库存储运费规则的 Embedding，用于语义检索。

### 决策

使用 Milvus Lite（`pymilvus[lite]`），零部署，纯 Python 运行。

**不采用** Milvus Standalone 的原因：
- 数据量极小：58个工作表，预估规则文本 < 1000 条
- 单用户自用系统，无并发压力
- Standalone 需要独立部署 Milvus 服务，增加运维成本
- 未来如需扩展到生产环境，Milvus Lite 的 API 与 Standalone 兼容，迁移成本低

### 后果

- ✅ 零部署，`pip install` 即可使用
- ✅ 单文件存储，便于备份和迁移
- ⚠️ 不支持分布式和高并发（当前场景不需要）
- ⚠️ 性能上限低于 Standalone（当前数据量下无影响）

## ADR-004: 通义千问全家桶（LLM + Embedding）

**状态**: 已采纳
**日期**: 2026-09-02

### 背景

需要 LLM 做意图识别和结果生成，需要 Embedding 模型做文本向量化。

### 决策

| 组件 | 选型 | 角色 |
|------|------|------|
| LLM | qwen3.7-max | 意图识别、工具调用、结果生成 |
| Embedding | text-embedding-v4 | 规则文本向量化 |

**不采用** OpenAI GPT-4o 的原因：
- 运费数据全中文，通义千问中文理解能力更强
- 通义千问价格更低
- 同一供应商简化 API 管理和计费

### 后果

- ✅ 中文场景理解更准确
- ✅ 统一 API Key（DASHSCOPE_API_KEY）
- ⚠️ 通义千问的 function calling 能力需验证
- ⚠️ 模型更新可能导致行为变化

## ADR-005: SQLite 作为费率数据存储

**状态**: 已采纳
**日期**: 2026-09-02

### 背景

费率数据需要结构化存储以支持精确查询（按国家、重量区间、货物类型筛选）。

### 决策

使用 SQLite 存储所有费率数据，通过 SQL 查询实现精确匹配和计算。

**不采用**直接运行时读取 XLS 的原因：
- XLS 解析慢，每次查询都要重新解析
- 无法高效索引和查询
- 合并单元格等格式问题导致解析复杂

**不采用** PostgreSQL 的原因：
- 单用户系统，无需多用户并发
- 需要额外安装和运维数据库服务
- 数据量小，SQLite 性能绑绑有余

### 后果

- ✅ 单文件部署，零运维
- ✅ SQL 查询灵活，支持复杂条件筛选
- ✅ 查询速度 < 10ms
- ⚠️ 不支持并发写入（当前场景不需要）

## ADR-006: Streamlit 作为 Web UI 框架

**状态**: 已采纳
**日期**: 2026-09-02

### 背景

需要一个 Web 界面让业务员方便使用，支持对话式查询和数据管理。

### 决策

使用 Streamlit 构建 Web UI，利用其 `st.chat_message` 组件实现聊天界面。

**不采用** Gradio 的原因：
- Streamlit 的聊天组件更成熟，社区生态更好
- Streamlit 的数据展示组件（表格、侧边栏）更丰富
- Streamlit 更适合构建"应用"而不仅是"demo"

### 后果

- ✅ 开发速度快，组件丰富
- ✅ 支持文件上传（数据导入场景）
- ⚠️ Streamlit 的单线程模型限制并发（单用户不影响）
- ⚠️ 自定义样式能力有限

## ADR-007: 目录表 + 费率表双重映射国家→渠道

**状态**: 已采纳
**日期**: 2026-09-02

### 背景

用户说"美国"，但"美国"的费率数据分散在多个工作表中（美国专线小包、TM美国专线Y2、欧美标准专线等），且部分工作表（如欧美标准专线）一个sheet包含20多个国家，每个国家价格不同。

### 决策

双重映射策略：
1. **目录工作表**：提取 产品类别 → 路向 → 渠道 的元数据关系
2. **各费率工作表**：从表头和数据行中提取精确的 国家 → 费率行 映射

### 后果

- ✅ 覆盖所有渠道和国家的对应关系
- ✅ 支持"一个sheet多国家"和"一个sheet一个国家"两种数据格式
- ⚠️ 解析逻辑需要针对每个工作表的格式做适配

## ADR-008: 硬编码货物类型映射 + LLM Fallback

**状态**: 已采纳
**日期**: 2026-09-02

### 背景

用户口语表达与数据中的行业术语不一致（如"衣服"→"P服装"，"电子产品"→"带电"）。

### 决策

两级映射：
1. **硬编码高频映射表**：覆盖常见说法（衣服→P服装，手机→带电，化妆品→膏体 等）
2. **LLM fallback**：硬编码表未命中时，交给 LLM 判断货物类型

### 后果

- ✅ 高频场景零延迟匹配
- ✅ 长尾场景由 LLM 兜底
- ⚠️ 需要维护映射表，随业务变化更新

## ADR-009: 默认实重计价 + 体积重提醒

**状态**: 已采纳
**日期**: 2026-09-02

### 背景

部分渠道按 `max(实重, 体积重)` 计费，体积重 = 长×宽×高(cm) / 8000。但用户通常不提供包裹尺寸。

### 决策

- 默认按用户提供的**实重**计算报价
- 如果该渠道有体积重计费规则，在结果中**提醒**用户："该渠道按体积重计费，如包裹体积重大于实重，实际费用可能更高"
- 如用户提供了尺寸信息，则自动计算体积重取较大值

### 后果

- ✅ 快速出报价，不增加对话轮次
- ✅ 提醒用户潜在差异，避免报价误导
- ⚠️ 最终费用可能与预估有差异（可接受，用户可复核）

## ADR-010: 统一费率计算模型，解析时归一化

**状态**: 已采纳
**日期**: 2026-09-02

### 背景

数据中有两种主要计费模式：
1. 单价模式：`运费/KG × 重量 + 处理费`
2. 首重续重模式：`首重价格 + ceil((重量-首重)/续重单位) × 续重单价`

数据中的表达方式多样："首0.5KG 77元，续0.5KG 21元"、"首重3KG56元，每续0.5KG加4.5元"等。

### 决策

设计统一费率模型，SQLite 中 `channels` 表包含两种模式的字段：
- 单价模式：`price_per_kg` + `handling_fee`
- 首重续重模式：`first_weight` + `first_weight_price` + `additional_weight` + `additional_weight_price`

XLS 解析时根据数据格式自动归一化到对应模式。计算时由统一的 `calculate_rate` 函数根据模式选择计算公式。

### 后果

- ✅ 计算逻辑统一，一个函数处理所有计费模式
- ✅ 解析时的归一化隔离了数据格式差异
- ⚠️ 解析器需要对每种格式做适配

## ADR-011: LangGraph State 自然管理多轮对话

**状态**: 已采纳
**日期**: 2026-09-02

### 背景

当系统追问货物类型后，用户回答"普货"，系统需记住之前的国家和重量，合并参数重新查询。

### 决策

利用 LangGraph 的 State 机制自然管理对话状态：
- State 中维护 `country`、`weight`、`cargo_type` 等字段
- 每轮对话由 `parse_intent` 节点更新 State（增量更新，不覆盖已有值）
- `check_params` 节点检查是否还有缺失参数，决定路由
- Streamlit 的 `st.session_state` 持久化 State 到会话级别

### 后果

- ✅ 多轮对话状态自动累积，无需额外管理
- ✅ 追问和回答自然融入工作流
- ⚠️ 需要确保 LLM 的意图识别不会误覆盖已有参数
